# kerbridge-setup — `kbsetup`, the tool that makes the thing exist

One binary. Every verb is idempotent.

```
kbsetup realm [--allow-example-realm]   provision if absent; verify and refuse if present
kbsetup directory                       the OUs, the service accounts, the delegation, the deny
kbsetup verify                          does durable state still match the config set
```

`--config <dir>` names the config set's directory; without it the compiled-in
`/etc/kerbridge` is used. Every verb reads the whole set **in process**, through
`kerbridge-core` — not through `kbconfig get`. The shell design this replaces
shelled out because shell cannot parse TOML; that reason is gone.

Installed at `/usr/sbin/kbsetup`, shipped by `kerbridge-issuerd`. `/usr/sbin`
rather than `/usr/bin` because it is root-only, which is FHS 3.0 §4.10's own
test — so the operator-facing tier spans two directories, `kbconfig` and
`kbmanage` being in `/usr/bin` where a non-root `PATH` can find them.

## setup → config → manage

`kbsetup` brings a deployment into existence, `kbconfig` owns its config set,
`kbmanage` runs it day to day. One tool per lifecycle phase, and each has a
different privilege position. That is why they are separate programs. This one
runs as root on the domain controller and creates things that cannot be
uncreated; `kbmanage` runs on an operator's own workstation as themselves;
`kbconfig` runs before either has anything to talk to.

## Why the verbs are separate

- **`realm` and `directory` are separate** because their lifecycles are. The
  realm is created once and never again; `directory` is re-run every time
  a cloud IdP is added. Merging them would buy one line in `SETUP.md` and cost
  the distinction.
- **`verify` is separate** because it is the only one that runs unattended, as
  `ExecStartPre=` on `kerbridge-issuerd.service`. The other two must never be on
  a start path.
- **There is no `provision` verb.** Provisioning is what `realm` does when there
  is no realm; verifying is what it does when there is. A third state sits
  between them: a `sam.ldb` with no [provision
  stamp](../../GLOSSARY.md#provision-stamp) beside it is a run that stopped
  partway, and every verb refuses it. GLOSSARY.md lists the
  spelling `kbsetup provision` under `avoid`.
- **There is no `kbdirectory` and no `kbrealm`.** One binary.

## What it does not do

It stops where the questions stop. `kbsetup verify` answers *does durable state
match the config set*; `kbmanage doctor` answers *can this identity reach that
file server*; `kbconfig check` answers *is the config set internally coherent*.
One question per tool, and no further checker grows.

It also seeds no users and no groups. A `kerbridge-sync` owns each source OU's
content and creates the admission group with its marker; `kbsetup directory`
creates the OU it writes into and the identity it binds as, and stops.

## Why it drives command-line tools

There is no Rust binding for `ldb` or `samdb` — crates.io has SMB *client*
crates only. So the directory work drives `samba-tool`, `ldbsearch` and
`ldbmodify`, and the durable-state comparison drives `testparm`. Two of the
behaviours it depends on were measured against the pinned baseline rather than
reasoned about — `dsacl set` re-applies cleanly and **prepends**, and the schema
write needs `--option=` and not `-o` — and re-deriving either in hand-rolled
descriptor code would buy nothing and lose the measurement.

**This crate does not depend on `ldap3`, and the absence is deliberate.**
Everything here runs against `sam.ldb` directly, as root, on the DC. That is the
one context in which the schema partition can be written at all, and it is the
context both measurements were taken in. A crate able to open an LDAPS
connection would invite half of this to be done remotely, and the half that
cannot be would then fail on a different host than the half that can.

## `kbsetup.8`

Generated by `clap_mangen` at build time from `src/cli.rs`, with no committed
copy — so it cannot go stale. `build.rs` writes `kbsetup.8` and one page per
verb into `OUT_DIR`; `cargo build -p kerbridge-setup --message-format=json` names
the directory. Nothing installs them yet.

## How Compose runs it

`deploy/realm/entrypoint.sh` calls `kbsetup realm`, and `deploy/realm/Dockerfile`
builds the binary into the image at `/usr/sbin/kbsetup`.

`kbsetup directory` runs in a container of its own — `docker compose run --rm
setup directory`, a `profiles:` service on the same image that exists for the
length of one command. It is not `docker compose exec` into a running service.
Writing a credential at `0640 root:<daemon group>` needs `CHOWN`, and `CAP_CHOWN`
is "arbitrary changes to file UIDs and GIDs" (`capabilities(7)`) — so a container
granted it defeats its own `cap_drop` for any file it can traverse to. Mounting
the secrets tree into a long-lived container would not be bounded by the
hardening, and would last the life of the install. A container that vanishes is
bounded by construction.

What it is handed is `secrets/generated/` and nothing else — the whole of what
this writes. The operator's IdP credentials sit under `secrets/idp/`, out of
reach, because they are authorities in a cloud tenant rather than in this realm.

`kerbridge-issuerd.service` carries `ExecStartPre=/usr/sbin/kbsetup verify`, so
the comparison runs at every issuer start. A host that is configured but not yet
provisioned is not a mismatch there: `verify` says so as a warning and exits 0,
because the fix is `kbsetup realm` and the unit would otherwise be down for the
whole of that documented step.
